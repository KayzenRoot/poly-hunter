# PH-M02-WO-001 CR-07 — advisory and fix revalidation

Checked 2026-10-07 against the exact final images and packages. These are primary vendor/upstream references; scanner output and advisories are evidence inputs, not approval.

## Residual findings and code paths

- **CVE-2026-95619 / GCC 14 libstdc++** — Red Hat describes an integer overflow in aligned `operator new` for particular large allocations. The exact final `libstdc++.so.6` SHA-256 is `972bb2a18b71140dab0240f8a1f68ab3fb1d56bcd4c4f824a91b70888faf5a00`. The aligned allocation symbol is present, but its disassembly validates alignment and calls `posix_memalign` with the requested size; it does not round the requested size upward or call the vulnerable `aligned_alloc` path. The same bytes were revalidated against the selected Trixie build. Proposed status is UNDER_INVESTIGATION with `NOT_AFFECTED` proposed, justification `vulnerable_code_not_present`; auditor and owner approval remain pending. Upstream description: <https://access.redhat.com/security/cve/cve-2026-95619>.

- **CVE-2026-85091 / development image Debian zlib** — Docker Scout identifies `zlib1g 1:1.3.dfsg+really1.3.1-1+b1`. The CVE trigger is `gzprintf`/`gzvprintf` after a non-blocking `gzwrite` stall. The exact Debian 1.3.1 source file lacks `gz_vacate`; upstream identifies non-blocking gz support as introduced in 1.3.1.2. Node separately embeds zlib `1.3.2.1-motley-8002e91`, but its v24.21.0 JS binding uses streaming `deflate`/`inflate` contexts and does not call or expose `gzprintf`/`gzvprintf`; the Node process does not dynamically link the system `libz.so.1`. No app source or provider dependency path calls those C APIs. Proposed status is UNDER_INVESTIGATION with `NOT_AFFECTED` proposed, justification `vulnerable_code_not_in_execute_path`; auditor and owner approval remain pending. Sources: <https://security-tracker.debian.org/tracker/CVE-2026-85091>, <https://sources.debian.org/src/zlib/1%3A1.3.dfsg%2Breally1.3.1-1/gzwrite.c/>, <https://github.com/madler/zlib/commit/81cc0bebedd935daeb81b0b6e475d8786b51af3d>, <https://github.com/madler/zlib/commit/df84af25dc1942490e1d1c899a07619152a46148>, <https://github.com/nodejs/node/blob/v24.21.0/src/node_zlib.cc>.

- **CVE-2026-85091 / PostgreSQL image Alpine zlib** — PostgreSQL image package is `zlib 1.3.2-r0`, and the library SHA-256 is `a1e2c03dcdedba98a06a00cadfb67a0e0b1cd93986860ec0c5ce66e789c44e57`. The vulnerable code is present in this package. Exact consumer symbol imports show `postgres` uses `deflate`; `pg_dump` and `pg_restore` use `gzwrite` and `gzopen`; none imports `gzprintf` or `gzvprintf`. The CVE-specific caller following a non-blocking write stall is absent from the installed consumer binaries. At runtime only PostgreSQL server processes run; `pg_dump`/`pg_restore` are not started by the app. PostgreSQL runs as UID 70 with zero effective capabilities, on the project-scoped Compose network with no host port published. Proposed status is UNDER_INVESTIGATION with `NOT_AFFECTED` proposed, justification `vulnerable_code_not_in_execute_path`; auditor and owner approval remain pending. The upstream zlib fix is commit `df84af25dc1942490e1d1c899a07619152a46148`; Alpine reports fixed package `1.3.2-r1`, but the official `postgres:17.11-alpine3.24` tag remains at the existing digest and contains `1.3.2-r0`.

## Trixie util-linux source reconciliation

The final Scout SARIF does not report util-linux HIGH/CRITICAL results. Debian's live tracker nevertheless marks exact Trixie package `2.41.5-0+deb13u1` affected by CVE-2026-76642, and the upstream range includes that version for CVE-2026-78408 and CVE-2026-78410. The component is installed and the relevant features are present, so scan omission is not claimed as a fix. The application execution path and preconditions were checked individually:

- **CVE-2026-76642** — requires an unprivileged caller to use SUID `mount(8)` with a root-controlled, fstab-authorized external helper entry and X-mount post-hook. Exact `/etc/fstab` is mode 0644 root:root and contains only the unconfigured-base comment; no `/sbin/mount.*` or `/usr/sbin/mount.*` helper exists in the image; application code does not invoke mount. No such entry can be changed by the UID-1000 service. Proposed status UNDER_INVESTIGATION, proposed `NOT_AFFECTED`, justification `vulnerable_code_cannot_be_controlled_by_adversary`.
- **CVE-2026-78408** — requires a privileged operator to execute `nsenter --join-cgroup` against an attacker-controlled target. `nsenter` is mode 0755, the application has no invocation path, PID namespaces are private, effective capabilities are zero, and `CAP_SYS_ADMIN` is absent from the container bounding set. Proposed status UNDER_INVESTIGATION, proposed `NOT_AFFECTED`, justification `vulnerable_code_cannot_be_controlled_by_adversary`.
- **CVE-2026-78410** — requires a root-controlled fstab-authorized restricted bind source plus an `X-mount.owner/group/mode` hook and attacker ability to replace the source or an ancestor. The exact fstab has no entries and is not writable by the service UID; app code does not invoke mount. Proposed status UNDER_INVESTIGATION, proposed `NOT_AFFECTED`, justification `vulnerable_code_cannot_be_controlled_by_adversary`.
- **CVE-2026-78409** — not carried as a final-image finding. Red Hat's advisory defines affected releases as v2.42 through v2.42.2 and explicitly says v2.40/v2.41 are not affected. The final image is v2.41.5; the old Bookworm scan's v2.38 row was a source/version mismatch, not a final-image disposition.

Official references: <https://security-tracker.debian.org/tracker/CVE-2026-76642>, <https://access.redhat.com/security/cve/cve-2026-78408>, <https://access.redhat.com/security/cve/cve-2026-78409>, <https://github.com/util-linux/util-linux/security/advisories/GHSA-m25x-3hj9-m26f>, <https://github.com/util-linux/util-linux/security/advisories/GHSA-rh77-686x-2f2m>, <https://tracker.debian.org/news/1793594/accepted-util-linux-2423-1-source-into-unstable/>.
