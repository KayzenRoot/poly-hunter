# Docker runtime validation WITH a test-only keyring

## Provisioning
- Two EPHEMERAL 32-byte AES keys generated in-memory and passed as environment
  variables to `docker compose`. They are NOT written to .env, NOT committed and NOT
  printed; they exist only for this probe and are discarded when the containers are
  recreated without them.
- Active key version: k2. Keyring carries k1 (previous) and k2 (active), so rotation has a
  real old key to fetch.

## Pre-state (no keyring): the vault fails closed
  GET /api/secrets -> HTTP 401 unauthenticated/provider_not_configured (auth provider absent,
  so the request never reaches the vault; the vault-unavailable path is proven by the
  dedicated test suite instead).

## The vault is CONFIGURED in the running container
Probed with the REAL keyring module inside polyhunter-web. The probe asks only for the
KeyObject TYPE, never the key bytes:

  isVaultKeyringConfigured(cfg) = true
  activeKeyVersion = k2
  versions = k1,k2
  resolveKey(k1) -> KeyObject type=secret symmetric=true
  resolveKey(k2) -> KeyObject type=secret symmetric=true
  resolveKey(k9) -> KEY_VERSION_UNAVAILABLE (fail closed)

## Client bundle: the keyring must NOT be reachable by a browser
apps/web/.next/static is the only directory a browser downloads. Scanned WHILE the
keyring is configured, so a leak would show up right here:

  POLYHUNTER_SECRET_ACTIVE_KEY_VERSION -> 0 client chunk(s)
