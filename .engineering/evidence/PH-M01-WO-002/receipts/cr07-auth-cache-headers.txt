1. THE CONTRACT
   @supabase/ssr 0.12.7 SetAllCookies is
     setAll(cookies: {...}[], headers: Record<string,string>)
   verified in node_modules/@supabase/ssr/dist/main/types.d.ts:23-58.
   The library delivers, on auth-cookie writes (dist/main/cookies.js:505-509):
     Cache-Control: private, no-cache, no-store, must-revalidate, max-age=0
     Expires: 0
     Pragma: no-cache

   The library's own type documentation states why this matters: responses that
   set auth cookies must not be cached by CDNs or reverse proxies, otherwise
   one user's session token can be served to a different user.

2. THE DEFECT
   apps/web/src/identity/supabase-adapter.ts declared "setAll(cookiesToSet)"
   and discarded the second argument. apps/web/proxy.ts already forwarded the
   delivered object directly and correctly needed no change.
   Consequence: Route Handlers that write Supabase auth cookies emitted
   responses carrying no anti-cache policy.

   The library was also measured to call setAll(x, {}) on its storage-only
   internal writes and to forward the policy only on the first cookie write per
   client instance. That is why a server client is created per request and why
   the Route Handler policy is applied unconditionally rather than depending on
   the library delivering headers on a particular call.

3. THE FIX (commit 0a76149)
   a) apps/web/src/identity/auth-cache-headers.ts (NEW, server-only)
      - AUTH_NO_STORE_HEADERS: frozen Record with the exact library policy.
      - applyAuthNoStoreHeaders(response): applies the policy, overwrites
        weaker pre-existing values, returns the same response for chaining.
      - NO mutable module state: a frozen constant plus a pure function that
        touches only the response argument. Concurrency-safe by construction.

   b) apps/web/src/identity/supabase-adapter.ts
      - setAll now declares (cookiesToSet, cacheHeaders) explicitly.
      - the delivered object is routed through recordAuthCookieMutation, which
        returns the centralized policy when it matches exactly and THROWS on
        any drift (missing no-store, extra header, changed value), surfacing a
        library upgrade instead of silently serving a weaker policy.
      - Empty deliveries ({} — the library's storage-only internal writes) also
        yield the centralized policy.

   c) DOCUMENTED BOUNDARY
      The next/headers cookie store exposes no response handle, so the adapter's
      setAll cannot write headers to the outgoing response. Cookies are written
      through the cookie store; the anti-cache headers are OBLIGATORILY applied
      by the Route Handler via the helper. This boundary is stated in the source
      of auth-cache-headers.ts and of the adapter.

   d) ROUTES COVERED (policy applied unconditionally on every response path)
      - /api/auth/login  : 302 PKCE redirect; 503 provider_unavailable;
                           503 provider-redirect mismatch.
      - /auth/callback   : 303 success; 303 denied; 303 invalid; 303 failed.
      - /api/auth/logout : 303 sign-out redirect.

      The callback denial / invalid / failure redirects also carry the policy: a
      failed exchange can still clear or rotate auth cookies, so a selective
      policy could serve a cookie-clearing redirect from cache.

   e) REFACTOR (no behavior change beyond the policy)
      login and the auth callback were extracted into handler.ts modules,
      matching the existing select-tenant / logout handler pattern, so the
      policy is testable without a provider or a database. The route files keep
      only wiring.
      logout previously set Cache-Control only; it now uses the helper and
      therefore also emits Expires: 0 and Pragma: no-cache.

   f) NOT TOUCHED
      CSRF (CR-02), RBAC, TenantContext, open redirect / trusted origin
      (CR-04), apps/web/proxy.ts, and everything under packages/ are unchanged.
      The callback's open-redirect and trusted-origin behavior is additionally
      asserted by a new test, proving the refactor did not weaken CR-04.
