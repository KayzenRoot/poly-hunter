## ACCEPTANCE MATRIX

### A. Cross-tenant isolation

Prove at least two tenants and multiple users/roles.

Attack every admitted tenant-scoped PH-M01 surface, including:
- tenant-scoped repositories;
- active tenant selection;
- `/api/me` tenant context exposure;
- secret collection metadata;
- single-secret metadata;
- secret create/replace/delete/rotate;
- internal `withDecryptedSecret`;
- direct id substitution;
- stale/foreign active-tenant cookie/selector;
- any server action/helper accepting tenant/user/secret ids.

Required properties:
- tenant A cannot read/write/list/rotate/delete/decrypt tenant B state;
- object ids are never authorization evidence;
- cross-tenant not-found behavior does not become an existence oracle;
- a client-supplied tenant/user/role cannot widen authority.

### B. Privilege escalation

Adversarially test:
- member -> admin/owner forged context;
- admin -> owner forged context where ownership-only semantics exist;
- platform_admin without tenant membership;
- client role field;
- user_metadata role injection;
- provider/user id substitution;
- role downgrade after context resolution;
- membership removal/suspension;
- user suspension;
- tenant suspension.

All must fail closed at the next authoritative operation.

### C. Session confusion / tenant selection

Attack:
- invalid auth cookie;
- stale/expired session state where test harness can represent it;
- missing verified subject;
- foreign tenant selector;
- suspended membership selector;
- malformed selector;
- logout/callback/open-redirect regressions;
- CSRF on state-changing auth/tenant routes;
- production trusted-origin behavior;
- same authenticated user switching between two valid tenants without cross-contamination.

No silent fallback to a different tenant after invalid/foreign selection.

### D. Authorization concurrency

Re-run and extend the two-connection PostgreSQL authority-window proof.

At minimum prove:
- role downgrade waits behind an in-flight sensitive operation;
- membership suspension waits;
- user suspension waits;
- tenant suspension waits;
- after pending authority change commits, the next operation is denied;
- lock ordering does not introduce a demonstrated deadlock cycle in the admitted PH-M01 paths.

Use deterministic synchronization / pg lock observation, not timing-only sleeps.

### E. Secret envelope adversarial acceptance

Re-prove:
- ciphertext tamper fails;
- tag tamper fails;
- nonce tamper fails;
- record-id AAD swap fails;
- tenant AAD swap fails;
- purpose AAD swap fails;
- wrong key fails;
- missing historical key version fails closed;
- nonce collision protection/retry still works;
- raw plaintext is not returned by any HTTP path;
- low-level decrypt/keyring primitives remain outside the public package surface;
- all secret API responses remain no-store.

### F. Plaintext / credential containment

Use high-entropy canary secret values created only for disposable tests.

Prove the canary is absent from:
- Git tracked files;
- generated evidence;
- application/server logs captured by the test harness;
- client bundle/build output;
- HTTP error bodies;
- HTTP metadata responses;
- snapshots;
- Docker/Compose configuration;
- Postgres plaintext columns / textual dumps outside encrypted ciphertext;
- JEV MCP inputs/receipts.

Also prove:
- `POLYHUNTER_SECRET_KEYRING_JSON` values are not committed;
- no secret/key variable is `NEXT_PUBLIC_*`.

Do not persist the canary in committed evidence.

### G. Migration + recovery drill

Use disposable databases only.

Required drill:
1. start from an empty PostgreSQL 17 database;
2. apply all versioned migrations;
3. create representative PH-M01 tenants/users/identity links/memberships/platform role as needed and encrypted secret fixtures through admitted application/repository paths;
4. capture a database backup using a supported PostgreSQL logical backup/restore path or an equally deterministic repository-approved recovery method;
5. destroy the disposable database;
6. restore into a fresh database;
7. verify schema constraints and PH-M01 records;
8. verify tenant isolation after restore;
9. verify encrypted secret metadata after restore;
10. with the correct test-only keyring, decrypt only through the authorized Vault callback and verify the test canary;
11. with a required old key version missing, prove recovery fails closed without data corruption;
12. no production credentials or persistent test keys.

If `pg_dump/pg_restore` are available in the canonical environment, prefer them.

### H. Rotation / recovery drill

Use TEST-ONLY key versions, e.g. v1 -> v2.

Prove:
1. create secret under v1;
2. preserve backup/recovery evidence;
3. switch active version to v2 while retaining v1;
4. rotate/re-encrypt atomically;
5. ciphertext/nonce/tag/key_version change as expected;
6. id/tenant/purpose/created_at remain stable;
7. plaintext can be consumed only through authorized callback;
8. remove v1 only AFTER all tested records are on v2;
9. if v1 is removed prematurely, affected record fails closed;
10. restore/reintroduce the correct test key and recover without rewriting corrupted metadata;
11. rotation after restore remains safe;
12. no secret appears in evidence/logs.

### I. Migration idempotency / roll-forward

Prove:
- empty DB migration;
- repeated migration path/no-op behavior;
- schema at expected version;
- no destructive rollback assumption is required if project policy is roll-forward;
- recovery guidance explains how to restore from backup and reapply current migrations;
- failed migration in a disposable scenario does not justify editing an already-applied migration in place.

Do not rewrite historical migration files merely to make the acceptance drill pass.
