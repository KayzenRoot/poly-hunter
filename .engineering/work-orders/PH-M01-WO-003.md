## CURRENT CRYPTO SOURCE CHECK

Revalidated 2026-10-06 against official Node.js 24 and NIST GCM guidance.

Implementation baseline:
- algorithm: `aes-256-gcm`;
- key length: exactly 32 bytes;
- IV/nonce: exactly 12 random bytes per encryption operation;
- authentication tag: exactly 16 bytes;
- IV generated with Node.js `crypto.randomBytes(12)`;
- use `createCipheriv` / `createDecipheriv` and explicitly set `authTagLength: 16`;
- AAD is mandatory and must be set before encryption/decryption finalization;
- authentication failure from `decipher.final()` fails closed;
- Node `KeyObject` / `createSecretKey` is preferred over passing secret strings directly to cipher APIs.

Official references:
- https://nodejs.org/download/release/v24.21.0/docs/api/crypto.html
- https://csrc.nist.gov/pubs/sp/800/38/d/final

NIST has announced a revision of SP 800-38D; the selected 96-bit IV and 128-bit tag remain compatible with the announced direction.

## ENVELOPE PROTOCOL V1

Protocol label:
`polyhunter-secret-envelope-v1`

AAD must be deterministic UTF-8 bytes and bind, in fixed order:
1. protocol label;
2. secret record id;
3. tenant id;
4. purpose;
5. key version.

Recommended canonical representation:
a JSON array with the exact ordered fields above and no optional fields.

A ciphertext copied to another secret id, tenant, purpose or key version MUST fail authentication.

## KEYRING

Server-only configuration. No key material in Postgres, Git, browser bundles, API payloads, logs, telemetry or evidence.

Admitted configuration names:
- `POLYHUNTER_SECRET_ACTIVE_KEY_VERSION`
- `POLYHUNTER_SECRET_KEYRING_JSON`

`POLYHUNTER_SECRET_KEYRING_JSON` is a JSON object mapping key version -> base64-encoded raw AES key.

Rules:
- no `NEXT_PUBLIC_*` secret variables;
- key versions match a constrained canonical identifier;
- every decoded key is exactly 32 bytes;
- active version MUST exist in the keyring;
- malformed/missing/duplicate-invalid configuration fails closed;
- local Docker base startup must remain healthy with the vault UNAVAILABLE when keyring config is absent;
- secret-dependent endpoints return a sanitized unavailable response when the keyring is unavailable;
- tests inject deterministic test keys directly; no real secret is committed.

## DATA MODEL

Add `encrypted_secrets` only for this Work Order.

Required fields:
- `id UUID PRIMARY KEY`;
- `tenant_id UUID NOT NULL` -> tenants, explicit delete/update behavior;
- `purpose VARCHAR(...) NOT NULL`;
- `ciphertext BYTEA NOT NULL`;
- `nonce BYTEA NOT NULL`;
- `auth_tag BYTEA NOT NULL`;
- `key_version VARCHAR(...) NOT NULL`;
- `created_at TIMESTAMPTZ NOT NULL`;
- `updated_at TIMESTAMPTZ NOT NULL`;
- `rotated_at TIMESTAMPTZ NULL`.

Constraints:
- purpose is canonical, nonblank and bounded;
- nonce length exactly 12 bytes;
- auth_tag length exactly 16 bytes;
- ciphertext must be nonempty;
- key_version canonical and bounded;
- add a UNIQUE constraint/index on `(key_version, nonce)` so accidental nonce reuse under one key version cannot persist;
- tenant-owned row always carries `tenant_id`.

Do not add trading_accounts, wallet data or provider credentials in this WO.

## AUTHORIZATION

Secret-management API operations require:
- a verified current identity;
- a freshly resolved active `TenantContext`;
- tenant role `owner` or `admin`.

`member` is denied.

Add explicit tenant capabilities as needed, for example:
- `secret:metadata`
- `secret:write`
- `secret:delete`
- `secret:rotate`

Do not grant these to `member`.

`platform_admin` does NOT automatically gain arbitrary tenant secret access and does NOT mint a TenantContext.

Every DB operation must revalidate current active tenant/user/membership state using the existing authoritative boundary.

## SECRET WRITE / MASKED API

Admit a minimal server API, no dashboard design:

- create/store secret;
- replace/update secret;
- list/get METADATA only;
- delete secret;
- rotate/re-encrypt secret to the active key version.

External responses may include only non-sensitive metadata such as:
- id;
- purpose;
- `configured: true`;
- timestamps;
- rotation status if needed.

External responses MUST NOT include:
- plaintext;
- ciphertext;
- nonce;
- auth tag;
- key material;
- provider credentials;
- plaintext length or secret-derived suffix unless explicitly justified.

There is NO HTTP plaintext read endpoint.

## INTERNAL SECRET USE

Internal secret consumption must be purpose-scoped and server-only.

Do not expose a generic "get plaintext string" API.

Preferred pattern:
- resolve a `SecretHandle` containing id + purpose + tenant binding;
- execute a short-lived callback such as `withDecryptedSecret(..., fn)`;
- provide plaintext as a Buffer/Uint8Array only inside that operation;
- best-effort zero temporary plaintext/key-decoding buffers in `finally`;
- never claim JavaScript can guarantee complete heap erasure.

No Polymarket adapter may call this vault in WO-003.

## INPUT RULES

- secret plaintext accepted as a bounded nonempty UTF-8 string/byte sequence;
- enforce a conservative maximum, e.g. 64 KiB;
- purpose must match a canonical lower-case identifier format;
- malformed inputs fail before encryption;
- do not trim or normalize secret plaintext;
- do not log request bodies or secret values.

## NONCE SAFETY

- fresh 12-byte cryptographically random nonce for EVERY encryption/re-encryption;
- never derive nonce from tenant/purpose/time/counter alone;
- DB unique `(key_version, nonce)` is a defense against accidental reuse;
- on an extremely rare nonce uniqueness collision, retry with a fresh nonce for a small bounded number of attempts, then fail closed;
- tests must inject a deterministic nonce source and prove retry/fail-closed behavior without weakening production randomness.

## ROTATION

Required before live credentials exist.

Single-record rotation path is sufficient for WO-003 if it is safe and auditable.

Rules:
- read + lock the authoritative tenant secret row;
- decrypt with the row's recorded old key version;
- encrypt with the ACTIVE key version and a fresh nonce;
- preserve id, tenant_id, purpose and created_at;
- update ciphertext, nonce, auth_tag, key_version, updated_at and rotated_at atomically;
- if already on active key version, return an explicit already-current result without unnecessary plaintext exposure;
- if old key version is missing, fail closed and do not mutate the row;
- corrupted tag/AAD/ciphertext fails closed and does not overwrite evidence;
- concurrent update/rotation must not create mixed envelope metadata.

A bulk rotation job is OUT OF SCOPE; WO-004 will drill/recovery-test the path.
