## OBJECTIVE

Implement the PH-M01 identity and authorization increment on top of the approved tenancy/persistence foundation:
- Supabase Auth behind an `IdentityPort` / provider adapter;
- cookie-based Next.js 16 server authentication;
- server-derived internal user identity;
- active tenant selection validated from active membership;
- explicit tenant RBAC plus separate `platform_admin`;
- minimal login/logout/auth callback shell;
- fail-closed behavior for invalid/stale auth or membership.

## CURRENT SOURCE CHECK

Official Supabase guidance revalidated 2026-10-05:
- `@supabase/ssr` remains beta/unstable and must remain adapter-isolated;
- Next.js 16 uses `proxy.ts` for SSR session refresh;
- `getClaims()` is the normal verified identity path; `getUser()` may be used for fresh provider user state;
- `getSession()` raw user/session data MUST NOT be trusted for authorization;
- browser configuration may contain project URL + publishable key only; secret/service-role keys must never enter client bundles;
- use PKCE-compatible SSR flows.

Execution MUST re-check official docs/changelog and exact npm package versions before mutation.

## SECURITY REQUIREMENTS

1. SEC-001, SEC-002, SEC-019, SEC-020, SEC-021, SEC-022 and SEC-024 are mandatory.
2. No authorization decision from client-provided user_id, tenant_id, role, JWT `user_metadata`, URL param, form field or local storage.
3. `user_metadata` is never authorization input.
4. `platform_admin` comes only from authoritative server-side `platform_roles`.
5. Tenant roles come only from authoritative active `tenant_memberships`.
6. Provider identity is accepted only after verified server-side Supabase authentication.
7. Never trust `getSession().user` for authorization.
8. Provider/network ambiguity is DENY / unauthenticated, never ALLOW.
9. Logout clears the application session path; invalid/expired/refreshed-failure sessions fail closed.
10. Membership suspension/removal takes effect on the next authoritative TenantContext resolution/repository operation.
11. Active-tenant cookie is httpOnly where feasible, SameSite appropriate, Secure in production, and never authorization proof by itself.
12. No access token, refresh token, auth code, password or secret key in logs/errors/telemetry/evidence.
13. No Supabase secret/service-role key in browser code, `NEXT_PUBLIC_*`, HTML or client bundle.
14. Local base startup must remain possible without real Supabase credentials; provider-dependent auth flows must fail closed/clearly unavailable, not fabricate identity.
15. No unsafe open redirect in auth callback/redirect parameters. Allow only same-origin relative paths or an explicit allowlist.
16. CSRF protections/framework same-origin guarantees must be reviewed for state-changing auth/tenant-selection actions.
17. HIGH/CRITICAL dependency/container findings block under ADR-0007 unless FIXED or policy-complete NOT_AFFECTED.
18. No wildcard scanner suppressions/ignores.

- explicit FK/delete behavior.

## IDENTITY LINKING

- canonical provider id: `supabase` unless existing frozen convention says otherwise;
- provider subject derives from verified Supabase subject only;
- lookup/create of internal user + identity_link must be transactional/idempotent and race-safe;
- duplicate provider subject must not create duplicate internal users;
- no tenant membership is auto-created from auth metadata;
- authenticated user with zero active memberships remains authenticated but has no TenantContext.

## ACTIVE TENANT

- selection may originate from a client selector;
- server resolves selected tenant against current active memberships;
- invalid/suspended/foreign tenant selection fails closed;
- stale selection must not silently fall back to a different tenant;
- tenant switch is explicit and revalidated.
